## Why MongoDB over SQL?

### 1. What is it?

MongoDB is a **NoSQL document database** that stores data as **JSON-like documents (BSON)** instead of rows and tables.

---

### 2. Why do we use it?

- Flexible schema (easy to change fields)
- Better for rapidly changing applications
- Scales horizontally (Sharding)
- Stores nested data naturally

---

### 3. Example

**SQL**

| id  | name    | amount |
| --- | ------- | ------ |
| 1   | Prakash | 500    |

**MongoDB**

```javascript
{
  _id: ObjectId("..."),
  name: "Prakash",
  amount: 500,
  method: "UPI",
  status: "SUCCESS"
}
```

You can later add a new field without changing the schema:

```javascript
{
  name: "Prakash",
  amount: 500,
  method: "UPI",
  status: "SUCCESS",
  couponCode: "SAVE10"
}
```

No table alteration is required.

---

### 4. Interview Point ⭐

**Use MongoDB when:**

- Data structure changes frequently.
- You need horizontal scaling.
- You're building applications like e-commerce, chat apps, social media, or MERN stack apps.

**Use SQL when:**

- Data is highly relational.
- Strong ACID guarantees across complex relationships are the priority (e.g., banking, ERP systems).

> **One-line interview answer:**
> **"I choose MongoDB over SQL when the application needs a flexible schema, faster development, and horizontal scalability. SQL is better for highly relational data and complex transactions."**

## Embedding vs Referencing

### 1. What is it?

It's how you model relationships between data in MongoDB.

- **Embedding** → Store related data inside the same document.
- **Referencing** → Store related data in separate collections and link them using an ID.

---

### 2. Why do we use it?

- **Embedding:** Faster reads, fewer queries.
- **Referencing:** Avoids duplicate data and is better for large or shared data.

---

### 3. Example

### ✅ Embedding

```javascript
{
  orderId: "ORD101",
  customer: {
    name: "Prakash",
    email: "prakash@example.com"
  },
  amount: 500
}
```

---

### ✅ Referencing

**customers**

```javascript
{
  _id: ObjectId("123"),
  name: "Prakash"
}
```

**orders**

```javascript
{
  orderId: "ORD101",
  customerId: ObjectId("123"),
  amount: 500
}
```

---

### 4. Interview Point ⭐

- **Embedding** → One-to-One or small One-to-Many relationships, data is always accessed together.
- **Referencing** → Large One-to-Many or Many-to-Many relationships, or when data is shared across documents.

> **Remember:**
> **Embed for speed. Reference for scalability.**

## What is an ObjectId?

### 1. What is it?

`ObjectId` is the **default unique identifier** for every document in MongoDB. It is stored in the `_id` field.

---

### 2. Why do we use it?

- Uniquely identifies each document.
- Automatically generated by MongoDB (unless you provide your own `_id`).

---

### 3. Example

```javascript
{
  _id: ObjectId("6892f4e0a1b2c3d4e5f67890"),
  paymentId: "PAY1001",
  amount: 500,
  status: "SUCCESS"
}
```

---

### 4. Interview Point ⭐

- Every document has a unique `_id`.
- If you don't provide `_id`, MongoDB creates an `ObjectId` automatically.
- `ObjectId` is **12 bytes** long and includes:
  - Timestamp (creation time)
  - Random value
  - Counter (to ensure uniqueness)

> **One-line interview answer:**
> **"ObjectId is MongoDB's default unique identifier for documents. It is automatically generated and guarantees uniqueness across documents."**

## How does Indexing work?

### 1. What is it?

An **index** is a data structure that helps MongoDB find documents **without scanning the entire collection**.

---

### 2. Why do we use it?

- Makes queries much faster.
- Improves search performance.
- Especially useful for large collections.

---

### 3. Example

Suppose your `payment` collection has **10 lakh documents**.

Without an index:

```javascript
db.payment.find({ paymentId: "PAY1005" });
```

MongoDB checks **every document** until it finds `PAY1005` (Collection Scan).

Create an index:

```javascript
db.payment.createIndex({ paymentId: 1 });
```

Now the same query:

```javascript
db.payment.find({ paymentId: "PAY1005" });
```

MongoDB uses the index to jump directly to the matching document (Index Scan).

---

### 4. Interview Point ⭐

- ✅ Index = Faster reads
- ❌ Indexes make **writes (insert/update/delete)** slightly slower because MongoDB must update the index too.
- Don't create indexes on every field—only on fields you frequently search, sort, or filter by.

> **One-line interview answer:**
> **"An index is a data structure that stores field values in sorted order, allowing MongoDB to locate matching documents quickly instead of scanning the entire collection."**

Yes, but with **only 10 documents you won't notice any performance difference**. The query is already so fast that indexing won't make a measurable impact.

Instead, you can **see whether MongoDB is using an index** by using `explain()`.

## Step 1: Check existing indexes

```javascript
db.payment.getIndexes();
```

You'll see only the default `_id` index.

---

## Step 2: Run the query without an index

```javascript
db.payment.find({ paymentId: "PAY1005" }).explain("executionStats");
```

Look for:

```javascript
"stage": "COLLSCAN"
```

`COLLSCAN` = Collection Scan (MongoDB checks every document).

---

## Step 3: Create an index

```javascript
db.payment.createIndex({ paymentId: 1 });
```

---

## Step 4: Run the same query again

```javascript
db.payment.find({ paymentId: "PAY1005" }).explain("executionStats");
```

Now look for:

```javascript
"stage": "IXSCAN"
```

`IXSCAN` = Index Scan (MongoDB uses the index).

---

## Step 5: Compare

### Before Index

```text
stage: COLLSCAN
```

### After Index

```text
stage: IXSCAN
```

---

### If you want to **see a real performance difference**, insert **100,000+ documents**.

For example:

```javascript
for (let i = 1; i <= 100000; i++) {
  db.payment.insertOne({
    paymentId: "PAY" + i,
    amount: Math.floor(Math.random() * 5000),
    status: "SUCCESS",
  });
}
```

Then run the same `find().explain("executionStats")` before and after creating the index. You'll see the number of documents examined drop dramatically, making the benefit of indexing much more obvious.

Yes. You can use **projection** on the output of `explain()`.

### Show only execution time

```javascript
db.payment.find({ paymentId: "PAY1006" }).explain("executionStats")
  .executionStats.executionTimeMillis;
```

---

### Show only the stage

```javascript
db.payment.find({ paymentId: "PAY1006" }).explain("executionStats").queryPlanner
  .winningPlan.queryPlan.stage;
```

If your MongoDB version doesn't have `queryPlan`, use:

```javascript
db.payment.find({ paymentId: "PAY1006" }).explain("executionStats").queryPlanner
  .winningPlan.stage;
```

---

### Show both together

```javascript
const result = db.payment
  .find({ paymentId: "PAY1006" })
  .explain("executionStats");

print(
  "Stage:",
  result.queryPlanner.winningPlan.queryPlan?.stage ||
    result.queryPlanner.winningPlan.stage,
);
print("Execution Time:", result.executionStats.executionTimeMillis, "ms");
```

**Expected output:**

Before index:

```text
Stage: COLLSCAN
Execution Time: 2 ms
```

After index:

```text
Stage: IXSCAN
Execution Time: 0 ms
```

> **Interview Tip:** Focus more on **`COLLSCAN` vs `IXSCAN`** than the execution time when testing with a small dataset. Execution time is meaningful only with thousands or millions of documents.

```javascript
// Remove an index by its name
db.payment.dropIndex("paymentId_1");
```

Or, using the index specification:

## What is the Aggregation Pipeline?

### 1. What is it?

The **Aggregation Pipeline** is used to **process and transform data** in multiple stages to produce a result.

---

### 2. Why do we use it?

- Filter data
- Group data
- Calculate totals, averages, counts
- Generate reports

---

### 3. Syntax

```javascript
db.collection.aggregate([{ stage1 }, { stage2 }, { stage3 }]);
```

---

### 4. Example

Calculate the **total payment amount** for all successful payments.

```javascript
db.payment.aggregate([
  {
    $match: {
      status: "SUCCESS",
    },
  },
  {
    $group: {
      _id: null,
      totalAmount: { $sum: "$amount" },
    },
  },
]);
```

Output:

```javascript
[
  {
    _id: null,
    totalAmount: 11296.98,
  },
];
```

---

### 5. Interview Point ⭐

- Aggregation works in **stages**.
- The output of one stage becomes the input of the next stage.
- Most commonly used stages:
  - `$match`
  - `$group`
  - `$project`
  - `$sort`
  - `$limit`
  - `$lookup`

> **One-line interview answer:**
> **"Aggregation Pipeline is a framework that processes documents through multiple stages to filter, group, transform, and analyze data."**

## 1. `$project`

### What is it?

Used to **select, remove, or rename fields** in the output.

### Why?

When you don't want to return all fields.

### Example

Return only `paymentId` and `amount`.

```javascript
db.payment.aggregate([
  {
    $project: {
      _id: 0,
      paymentId: 1,
      amount: 1,
    },
  },
]);
```

**Output**

```javascript
{
  paymentId: "PAY1001",
  amount: 499.99
}
```

### Interview Point ⭐

- `1` → Include field
- `0` → Exclude field

---

## 2. `$sort`

### What is it?

Used to **sort documents**.

### Why?

To display data in ascending or descending order.

### Example

Sort by amount (highest first).

```javascript
db.payment.aggregate([
  {
    $sort: {
      amount: -1,
    },
  },
]);
```

- `1` → Ascending
- `-1` → Descending

### Interview Point ⭐

```javascript
{
  $sort: {
    amount: 1;
  }
} // Lowest to Highest
{
  $sort: {
    amount: -1;
  }
} // Highest to Lowest
```

---

## 3. `$limit`

### What is it?

Returns only the **first N documents**.

### Why?

Used for Top N records or pagination.

### Example

Get the top 3 most expensive payments.

```javascript
db.payment.aggregate([
  {
    $sort: {
      amount: -1,
    },
  },
  {
    $limit: 3,
  },
]);
```

### Interview Point ⭐

`$limit` is usually used **after `$sort`**.

---

## Real Interview Example

**Find the top 3 successful payments and return only `paymentId` and `amount`.**

```javascript
db.payment.aggregate([
  {
    $match: {
      status: "SUCCESS",
    },
  },
  {
    $sort: {
      amount: -1,
    },
  },
  {
    $limit: 3,
  },
  {
    $project: {
      _id: 0,
      paymentId: 1,
      amount: 1,
    },
  },
]);
```

This single query demonstrates the use of **`$match` → `$sort` → `$limit` → `$project`**, which is a very common interview pattern.

## `$lookup` vs `populate()`

### 1. What are they?

- **`$lookup`** → MongoDB Aggregation stage used to join two collections.
- **`populate()`** → Mongoose method that automatically fetches referenced documents.

---

### 2. Why do we use them?

Both are used to retrieve related data from another collection.

---

### 3. Example

Suppose you have:

**customers**

```javascript
{
  _id: ObjectId("C1"),
  name: "Prakash"
}
```

**orders**

```javascript
{
  customerId: ObjectId("C1"),
  amount: 500
}
```

### Using `$lookup`

```javascript
db.orders.aggregate([
  {
    $lookup: {
      from: "customers",
      localField: "customerId",
      foreignField: "_id",
      as: "customer",
    },
  },
]);
```

---

### Using `populate()` (Mongoose)

```javascript
Order.find().populate("customerId");
```

---

### 4. Interview Point ⭐

| `$lookup`                 | `populate()`                        |
| ------------------------- | ----------------------------------- |
| MongoDB feature           | Mongoose feature                    |
| Uses Aggregation          | Uses Mongoose ORM                   |
| Faster for complex joins  | Easier to write                     |
| Works directly in MongoDB | Works only in Node.js with Mongoose |

### One-line interview answer

> **"`$lookup` is MongoDB's aggregation stage for joining collections, whereas `populate()` is a Mongoose convenience method that automatically replaces referenced IDs with the related documents."**

Sure—here it is as a writing block.

Yes, you can. In fact, that's the correct approach:

```
customers
    │
    ▼
orders
    │
    ▼
products
```

However, your second `$lookup` has two issues:

1. `foreginField` is misspelled. It should be `foreignField`.
2. You're trying to join `customers` directly to `products` using `_id`, but the `productIds` are inside the **order**, not the customer.

You need to use `order.productIds` as the `localField`.

### Correct Query

```javascript
db.customers.aggregate([
  {
    $lookup: {
      from: "orders",
      localField: "customerId",
      foreignField: "customerId",
      as: "order",
    },
  },
  {
    $unwind: "$order",
  },
  {
    $lookup: {
      from: "products",
      localField: "order.productIds",
      foreignField: "_id",
      as: "products",
    },
  },
  {
    $project: {
      _id: 0,
      name: 1,
      email: 1,
      "order.orderId": 1,
      products: {
        $map: {
          input: "$products",
          as: "product",
          in: {
            name: "$$product.name",
            price: "$$product.price",
          },
        },
      },
    },
  },
]);
```

### Example Output

```javascript
[
  {
    name: "Rahul Sharma",
    email: "rahul@example.com",
    order: {
      orderId: "ORD001",
    },
    products: [
      {
        name: "iPhone 16",
        price: 85000,
      },
      {
        name: "Wireless Mouse",
        price: 2000,
      },
    ],
  },
];
```

### Why use `$map`?

A `$lookup` returns the **entire product documents**. If you only want specific fields like `name` and `price`, `$map` lets you transform the array into just those fields.

This is a common and clean approach in MongoDB aggregation pipelines.

### Even Better (Interview-Level)

An even more advanced solution is to use the **pipeline form of `$lookup`** so that MongoDB returns only `name` and `price` directly from the `products` collection, instead of fetching the full documents and then projecting them. This is a frequently asked MongoDB interview topic because it's more efficient.

## How do Transactions work?

### 1. What is it?

A **transaction** ensures that **multiple database operations either all succeed or all fail**.

---

### 2. Why do we use it?

To keep data consistent when updating multiple collections.

---

### 3. Example

Suppose a customer buys a product:

- ✅ Create an order
- ✅ Reduce product stock
- ✅ Save payment

If payment fails, **none of the changes should be saved**.

```text
Start Transaction
    ↓
Create Order
    ↓
Update Product Stock
    ↓
Save Payment
    ↓
Commit ✅
```

If payment fails:

```text
Start Transaction
    ↓
Create Order
    ↓
Update Product Stock
    ↓
Payment Failed ❌
    ↓
Rollback
```

The order and stock update are undone.

---

### 4. Basic Mongoose Syntax

```javascript
const session = await mongoose.startSession();

session.startTransaction();

try {
  // Multiple operations

  await session.commitTransaction();
} catch (err) {
  await session.abortTransaction();
} finally {
  session.endSession();
}
```

---

### 5. Interview Point ⭐

- Use transactions when **multiple collections/documents must stay consistent**.
- If one operation fails, MongoDB **rolls back** all previous operations in the transaction.

> **One-line interview answer:**
> **"A transaction groups multiple database operations into a single unit of work, ensuring either all operations are committed or all are rolled back if any operation fails."**

If you're using **MongoDB Shell (`mongosh`)**, you can write a transaction like this:

```javascript
const session = db.getMongo().startSession();

session.startTransaction();

try {
  const orders = session.getDatabase("yourDatabase").orders;
  const products = session.getDatabase("yourDatabase").products;
  const payments = session.getDatabase("yourDatabase").payments;

  orders.insertOne({
    orderId: "ORD101",
    productId: "P1",
    customerId: "C1",
    amount: 500,
  });

  products.updateOne({ _id: "P1" }, { $inc: { stock: -1 } });

  payments.insertOne({
    paymentId: "PAY101",
    amount: 500,
    status: "SUCCESS",
  });

  session.commitTransaction();
  print("Transaction committed");
} catch (err) {
  session.abortTransaction();
  print("Transaction aborted");
}

session.endSession();
```

### Interview Point ⭐

A transaction in MongoDB is simply a group of normal commands (`insertOne`, `updateOne`, `deleteOne`, etc.) executed inside a transaction. If any command fails, `abortTransaction()` rolls back all the previous operations.
